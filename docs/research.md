# 领域调研与设计取舍

> 目的：说明“为什么这样设计、为什么不引现成库”以及关键取舍依据。

## 1. 主流方案盘点

| 方案 | 定位 | 依赖 | 与底座契合度 |
| --- | --- | --- | --- |
| bwmarrin/snowflake | 雪花 ID | 0 | 功能接近，无回拨策略/解析，风格不一致 |
| sony/sonyflake | 雪花变体（时间+机器+序列） | 0 | 用 39 位时间戳，回拨处理简单 |
| segmentio/ksuid | 可排序唯一 ID（20 字节） | 0 | 时间有序，但非雪花语义 |
| google/uuid | UUID v4/v7 | 0 | 无序/部分有序，不适合主键排序 |
| 美团 Leaf / 百度 UidGenerator | 分布式发号 | 重 | 依赖 DB/ZK，明显过度 |

## 2. 自研结论

自用项目需要的是**轻量、可配置、有回拨防护**的雪花与短 ID，
现成雪花库要么缺少回拨策略，要么无法配置位布局，且错误语义
与 errx/logx 不一致。自研成本低（核心几十行），可以做到：

- 位布局/纪元/回拨策略全部可配；
- 与 errx/logx 生态原生打通；
- 短 ID 与雪花同库提供，风格统一；
- 0 第三方依赖，质量门禁对齐底座标准。

## 3. 关键取舍

### 3.1 位布局：默认 41/10/12

41 位毫秒时间戳约 69 年（自 2024 年起至 2093 年），10 位节点
支持 1024 节点，12 位序列单毫秒 4096 个——覆盖自用多实例与
单机高并发；业务规模特殊时可按位重配。

### 3.2 回拨策略：默认等待

生产环境中 NTP 校时常见毫秒级回拨；默认等待（5ms 上限）在
绝大多数场景透明恢复；严格场景可切 Reject；测试/容忍场景
可用 Loose。三种策略覆盖全部现实情况。

### 3.3 序列重启随机起点

进程重启后序列从随机值开始，避免同毫秒内从 0 递增导致
ID 可预测；时间戳+节点仍保证不碰撞。

### 3.4 短 ID：base62 + 可排除易混字符

短 ID 用于邀请码/短号，base62 紧凑（8 位约 2.18×10^14 空间）；
`AlphabetNoConfusable` 排除 `0O1lI` 等，提升人工录入正确率；
碰撞检测由业务回调 + 重试完成（库不查库，保持薄）。

### 3.5 并发：互斥锁

生成路径为纯整数运算，互斥锁临界区纳秒级，目标 ≥2M IDs/s
已远超自用需求；不引入无锁 CAS（复杂度与收益不成比例）。

## 4. 与既有底座的分工

| 底座 | 分工 |
| --- | --- |
| errx | idgenx 全部错误语义与错误码 |
| logx | 结构化日志（回拨告警、失败、碰撞重试） |
| dbx | 业务用 idgenx 生成主键后经 dbx 落库 |
| cachex | 短 ID 唯一性检查可配合 cachex 去重（业务组合） |
| confx | 业务用 confx 加载节点/位数配置后传入 |
| resiliencex | 回拨等待可视为容错语义的补充，不重复实现 |
